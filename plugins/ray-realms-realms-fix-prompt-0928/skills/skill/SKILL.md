請直接在目前的課程平台專案中，**修復浮水印誤判導致影片永久停播的根本設計問題**，並修正課程播放頁的 Safari 相容性與 RWD。請實際修改程式、啟動本地服務、重現問題、完成測試，不要只給建議或叫學員換瀏覽器。

### 最高優先：浮水印不能剝奪已購課學員的播放權利

已知症狀：合法學員在播放頁看到「偵測到浮水印保護被破壞，這支影片已在本次頁面中下架。請重新整理」，更換第三方 Cookie 設定或使用無痕模式仍可能發生。另有 Safari 排版異常回報。

核心設計要求：

- 浮水印是顯示層的外流嚇阻措施，CSS／DOM 異常應進入**自動修復**流程。
- **任何浮水印偵測結果都不能永久鎖死、移除、重新建立或暫停已授權播放器，也不能讓播放按鈕失效。**
- 保留個人化浮水印、時間戳、移動與設定功能；不能以全面關閉浮水印、隱藏錯誤訊息或延長停播倒數交差。
- 登入、購課授權、受限影片 API 與簽名 URL 驗證繼續由伺服器負責，不得移除或改為公開影片來源。
- 不得宣稱網頁 DOM 浮水印能可靠偵測錄影、提供 DRM 或完全杜絕外流。

### 第 1 步：辨識版本、保留現有變更、隔離測試環境

1. 讀取專案的 AGENTS.md、package.json、相關播放器程式與現有測試，記錄目前分支、版本及工作目錄變更。保留使用者未提交的工作，不要還原或覆蓋不相關修改。
2. 搜尋下列符號／文字定位程式：`VideoWatermarkOverlay`、`tamperPauseEnabled`、`onTamper`、`watermarkTampered`、`maskImage`、`getComputedStyle`、`偵測到浮水印保護被破壞`。
3. 常見檔案如下，若不存在就搜尋實際對應位置，不能直接照路徑盲改：
   - `components/main/player/video-player.tsx`
   - `components/main/player/video-watermark-overlay.tsx`
   - `lib/video-watermark.ts`、`lib/video-watermark-guard.ts`
   - `components/admin/courses/course-details-form.tsx`
   - `components/main/player/player-layout.tsx` 及同目錄的 sidebar、content、menu、popover 元件
   - `app/globals.css`、影片授權 route 與 server actions
4. 必須啟動本地服務，資料庫使用新建的本地測試資料庫，只建立合成管理員、已購課學員、未購課學員及測試課程。使用公開示範影片或已明確授權的測試影片，不複製真實客戶資料。
5. 不可直接載入整份正式環境檔；不使用正式資料庫。若使用者另行授權參考 Cloudflare／R2 變數，只讀取必要的允許清單欄位，資料庫連線必須獨立指定並在執行 migration、seed 或其他寫入前檢查 hostname 與資料庫名稱。不印出金鑰、完整連線密碼或簽名 token。
6. 先讀 build／啟動 scripts：某些版本的 `pnpm build` 會自動 migration 或把環境設定同步進 DB。確認本地隔離後才執行，不能把建置誤當成純唯讀檢查。
7. 紀錄本地驗收 URL 與重現步骤。測試注入功能只能在測試／開發環境存在，不能讓正式站暴露任意修改浮水印或讀取測試憑證的入口。

### 第 2 步：先重現舊版浮水印誤判，建立失敗測試

逐項閱讀現有判斷，不要先認定 Cookie 或使用者破解：

1. **不支援 CSS 屬性**：`getComputedStyle(...).maskImage` 在某些瀏覽器／版本可能是 `undefined` 或空字串。若直接用 `!== 'none'` 判定遮罩，就會把正常浮水印當成遭破壞。也檢查 `webkitMaskImage`、`clipPath`、`webkitClipPath`、`filter`、`mixBlendMode`。
2. **數值前綴誤判**：`filter.includes('opacity(0')` 會誤判仍可見的 `opacity(0.8)`；檢查 brightness 是否有同類問題。`transform.startsWith('matrix(0')` 會誤判縮放或旋轉，不可把字串前綴等同完全不可見。
3. **生命週期誤判**：初次渲染、iframe 非同步載入、短暫零尺寸、尺寸切換、全螢幕、迷你播放器、背景分頁、休眠恢復，都可能暫時無法取得可靠幾何尺寸。
4. **永久停播路徑**：追蹤回呼如何一路設定 tampered state、pause、disabled、提前 return 錯誤畫面或卸載 iframe。檢查專案所有影音供應商分支。
5. 建立可重複的單元測試與本地瀏覽器測試入口。模擬缺少 `maskImage` 時，保留其他真實 computed style；確認舊版會經過原本門檻而停播，修正版在同條件不會。模擬環境相容性缺陷不等於已證實學員當時的瀏覽器版本，報告中分清楚。

### 第 3 步：把浮水印偵測與播放授權徹底分開

1. 移除由浮水印觸發的永久停播狀態、影片卸載、SDK pause、控制列 disabled 與播放 handler 的拒絕分支。保留真正的載入失敗、授權失敗、供應商錯誤處理。
2. 讓浮水印元件負責偵測與修復自己的顯示；對外只回報修復原因，例如 `onRepair(reason)`，不回傳禁止播放的指令。
3. 每次修復維持同一個影片 iframe／SDK 實例，不切換 key、不重載影片 URL、不重建播放器。播放秒數、音量、倍速與進度追蹤須保持正常。
4. 診斷事件須節流，例如最多每 60 秒一次；只記錄必要的原因碼與非敏感識別，不附學員 Email、完整簽名播放 URL、token 或浮水印全文。
5. 相容既有設定：若資料庫已有 `tamperPauseEnabled`，可先保留欄位作為自動修復開關，以避免不必要的資料遷移；同步更新型別註解與後台文案為「自動修復浮水印」，說明不會因此中斷播放。不得讓舊欄位仍在某個 provider 分支執行停播。

### 第 4 步：實作可恢復、跨瀏覽器的浮水印顯示機制

1. 抽出可測試的 CSS 判斷函式。缺少／空值的屬性視為「無足夠證據」，不可直接判定破壞；同時檢查標準與 WebKit 前綴。以明確的隱藏狀態、解析後數值及實際幾何範圍判斷，避免字串前綴猜測。
2. 只有在文件可見、容器連接 DOM、影片方框尺寸可測量時累計連續異常；用 `performance.now()` 計時。恢復正常、visibility 改變、零尺寸、超過觀察間隔的休眠／排程落差，都重置異常累計。
3. 保留適度連續觀察門檻，讓一般排版過渡完成。持續異常後恢復浮水印的父子關係、class、inline style、透明度、文字與位置。修復失敗後可再次嘗試，不能設一次性失敗鎖。
4. 防止 React reconciliation 崩潰：浮水印文字節點被外掛刪除後，不要讓 React 繼續更新已不存在的子節點。可由 React 持有穩定的空外層 div，受控的修復函式以 `textContent`／DOM API 管理其內文；或採其他有測試支持的穩定方案。不要用未清理的 innerHTML 插入使用者資料。
5. 處理整個浮水印 root 被移除、文字被移除、display:none、opacity:0、移出影片、clip／mask、父層重排。修復只動浮水印，不干預播放器。也要驗證節點遭移除後 React unmount／換課不會拋錯。
6. 以真正影片方框計算位置，尤其全螢幕直向的上下黑邊；按影片寬度限制浮水印寬度並允許長文字換行。尺寸變更時立即重新定位，避免沿動畫軌跡跑到黑邊。
7. MutationObserver 回呼去抖、避免自行修復觸發無限迴圈；ResizeObserver、interval、timeout、visibility listener 在卸載時全部清除。避免每次 render 重建監聽器。
8. 對原本就關閉浮水印或自動修復的課程保留合理的設定語意；不可為了通過測試強制關閉保護。

### 第 5 步：驗收浮水印，必須在真實播放期間測試

以下每項逐一留下「操作 → 預期 → 實際 → 證據」，未完成就標示待驗證：

- 單元測試：缺少／空 CSS 屬性；標準及 WebKit 前綴；`opacity(0.8)`、`brightness(0.9)` 不誤判；真正隱藏可修復；計時器在正常、背景、零尺寸與休眠時重置。
- 本地瀏覽器：同一個舊版失敗條件下連續播放至少 2 分鐘，超過原本停播門檻；進度持續前進且沒有永久錯誤畫面。
- 播放中依次刪除浮水印 root、刪除文字、隱藏、設透明、移出畫面；每次都恢復可見並繼續播放。記錄 iframe／播放器實例是否不變，不能只看「畫面有影片」。
- 暫停／繼續、快轉、倍速、音量、全螢幕進出、迷你播放器、旋轉／縮放、背景分頁、零尺寸後恢復、切換單元，都不讓影片進入永久停播狀態。
- 未登入仍導向登入或拒絕受限來源；已登入未購課仍拒絕受限來源與串流 API；已購課能播放。試看權限依原設計保留。
- 專案啟用的 YouTube／Vimeo／Cloudflare Stream／其他 provider 都要檢查。沒有憑證或可用影片時，明確分開「程式審查已通過」與「實播待驗證」，不能用 YouTube 測試代替其他 provider 的實播結論。

### 第 6 步：修復整個課程播放頁 RWD

請在真正的 `/courses/[slug]/lessons/[id]` 測試，不只看獨立播放器 demo。涵蓋章節側欄、播放器、上一堂／下一堂操作列、講義、目錄、留言、私訊、回頂部及迷你播放器。

1. 手機／平板側欄改抽屜，避免中等寬度仍塞進過寬固定側欄；桌面側欄可收合，寬度按斷點調整。長課程名稱與章節名稱不推寬頁面，計數及圖示不被壓扁。
2. 影片保持比例。以**實際播放器容器寬度**決定精簡控制列，不只看視窗寬度；窄畫面保留播放、進度、時間、靜音、倍速及全螢幕，非必要音量滑桿可收合。避免按鈕換兩行或超出邊界。
3. ResizeObserver 只註冊必要數量，需涵蓋 Cloudflare 等非同步載入後才出現的容器；卸載時清除。
4. 窄螢幕浮動工具列須完整顯示，四個操作可點擊，不以固定大 padding 推出螢幕。處理 safe-area；回頂部按鈕在窄畫面放工具列上方。頁尾保留空間，最後一段內容可捲到工具列上方。
5. 768／820px 平板捲動後，迷你播放器不得與底部工具列或回頂部按鈕重疊。留意祖先的 transform／will-change／overflow 對 fixed 全螢幕容器的影響，實際驗證迷你播放器進全螢幕能覆蓋視窗。
6. 橫向短視窗可取消影片 sticky，避免佔滿可閱讀高度。目錄跳轉應根據實際 computed position 計算遮擋高度，不可只按 class 字串或螢幕寬度推算。
7. 目錄、留言、私訊設明確關閉按鈕、可用高度與內部捲動；處理可視區、碰撞邊距、safe-area。確保關閉、輸入與送出控制不被裁切。關閉後必須確認面板真的消失，切換留言／私訊時只能留一個開啟面板；若退場動畫造成殘留，可依 open 狀態直接卸載內容，避免依賴 animationend 事件。測試開關即可，不要真的寄私訊或留言給客戶。
8. 講義容器使用 min-width:0 與適當長字串換行；表格、程式碼在自身區域水平捲動。不可只對整頁加 overflow-x:hidden 掩蓋被裁掉的內容。
9. 製作中單元的影片佔位保留實際高度與比例，不能因 absolute child 讓容器塌陷。

### 第 7 步：Safari 與解析度驗收

至少檢查以下 CSS viewport 尺寸，確認實際 `innerWidth/innerHeight`，不要把 Retina 實體像素或瀏覽器縮放後視窗尺寸混在一起：

`320×568、375×667、390×844、414×896、667×375、844×390、768×1024、820×1180、1024×768、1280×800、1440×900、1920×1080、2560×1440`。

每個尺寸確認沒有整頁水平溢出、工具列在視窗內。窄手機、橫向、平板、桌面至少各自實際操作課程列表、目錄、留言／私訊開關、捲動與全螢幕，而不只量 scrollWidth。用長標題、長網址、寬表格和長程式碼測試。

Safari 必須額外注意：

- 記錄真實瀏覽器版本；Chrome 裝置模式不能代表 Safari。能使用本機 Safari 就直接測，也可用 Safari 回應設計模式；這仍不等於真機 iOS 或所有歷史 Safari。
- 若工具列跑到左上角，讀取元素的 computed position／top／right／bottom／left，核對瀏覽器實際載入的 CSS 規則與伺服器提供的 CSS。分辨「規則未載入」、「樣式被覆寫」、「瀏覽器不支援語法」、「定位父層改變」。
- 本地開發曾出現 Safari 留著舊版樣式表：新 DOM class 已出現，但 CSSOM 缺少新規則；從來源重新載入後恢復。這只能證明那次本地熱更新問題，不能推論正式站或學員當時也是快取問題。不要把「叫所有人清快取」當永久修正。
- 正式模式需驗證冷載入的 CSS／JS 版本一致；若實際支援範圍含較舊 Safari，確認依賴與 CSS 語法相容性並實作必要 fallback。不要為了消掉單一症狀隨意降級整個 Tailwind 或重寫全站。
- 如果拿不到受影響學員的瀏覽器版本／錄影，明確列為未知，先完成可證實的程式缺陷修復。

### 第 8 步：交付修正與可核對的證據

1. 跑浮水印回歸測試、TypeScript、修改檔案 ESLint、`git diff --check`；檢查瀏覽器 console 的新增應用程式錯誤。若有既存 warning，清楚區分。
2. 再檢查 diff，確認沒有把正式 .env、個資、憑證或測試登入入口加入版本控制。盡量不新增依賴、不調整無關功能、不做無關資料庫 migration。
3. 交付原因與觸發路徑、修改檔案、修正後行為、實際執行的測試及結果、瀏覽器／尺寸矩陣、仍待驗證事項、本地驗收 URL。
4. 完成標準是「浮水印顯示可恢復，影片與合法觀看權限不中斷」，不是「錯誤字樣消失」。RWD 成功也必須有實際互動證據。

請按上述順序開始：先找出浮水印與永久停播的因果路徑，重現，再完成核心修復與驗收，最後處理 RWD 並交付結果。除非確實缺少必要資訊，否則持續實作到完成。
